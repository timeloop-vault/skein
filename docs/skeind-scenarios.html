skeind: scenarios

The goal is for harnesses to run somewhere other than the machine showing the UI, and to keep running with no client attached. skeind is the daemon that makes that possible: it owns rooms, PTYs, transcript tails and the agent API, and one or many clients attach to it. These diagrams walk from today's single process to remote rooms, cross-daemon routing and unattended approvals.

  • client (UI)
  • skeind (daemon)
  • harness (agent CLI)
  • machine or neutral
  • problem or blocked

1. Today

One Skein process holds the webview UI and the Rust backend: PTYs, transcript tails, the agent API on loopback, the watcher and sqlite. Harnesses are its child processes and call MCP and hooks back on 127.0.0.1.

What changes

  • Nothing yet; this is the baseline.
  • Problem: quit the app and every harness dies, and nothing can run on another host.

2. Attached local (Phase 1)

The backend is extracted as skein-daemon and embedded in the app. The UI talks to it through the same protocol it will later use over a socket, but over an in-process transport.

What changes

  • Zero behaviour change; the seam is in place.
  • The UI no longer owns rooms, PTYs or the database.
  • Still one process: quit still ends the harnesses.

3. Detached local (Phase 2)

skeind runs as its own process over a local socket and outlives the app. It keeps a headless terminal emulator per PTY so a returning client can be shown the screen as it is now.

What changes

  • Closing the UI no longer stops harnesses.
  • Reattach: connect, send since=<seq> for missed events, then per terminal a snapshot and live bytes.
  • Settings chooses attached or detached.

4. Local and remote rooms (Phase 3)

A second skeind runs on an always-on host with a workspace root of main checkouts. The client connects to every daemon directly over WebSocket on a private overlay network, authenticated by a device token.

What changes

  • Rooms can live on either host; a host picker appears at room creation.
  • Each harness talks MCP and hooks to the skeind next to it on 127.0.0.1; no reverse tunnels.
  • Terminal bytes flow only between client and the daemon that owns the PTY.

5. Cross-daemon routing (Phase 3b)

The local skeind dials out to each remote skeind. That link carries routed agent-API traffic both ways but never terminal bytes. A harness only ever talks to its own daemon, which forwards.

What changes

  • send_message, create_room, close_room, open/close_harness and list_rooms aggregation route across daemons.
  • Room ids are daemon-qualified; the owning daemon is authoritative for mailbox, sign-off and createdBy.
  • Mail to an unreachable daemon queues on the sender's daemon and is delivered on reconnect; create and close fail with "daemon offline".

6. Unattended approval (Phase 4)

When a harness on the remote skeind hits a permission dialog, the hook blocks and an approval record enters the event stream. A notifier pushes it through a self-hosted push service; any client may answer.

What changes

  • Approvals survive with no client attached.
  • First answer wins; an optional per-room timeout policy can decide when nobody answers.
  • The same event stream feeds every attached client.

7. Summary: what moves

Everything that owns state or runs agents moves into skein-daemon. Everything that draws, or belongs to the desktop window, stays in the client.

What changes

  • Moves: rooms and sqlite, PTY host, transcript tails, watcher, git reads, files backend, review, agent API and MCP, design preview server, spawn env probe.
  • Stays: window, xterm.js and CodeMirror rendering, updater, clipboard, OS notifications, settings UI.
  • Each phase is usable on its own.
