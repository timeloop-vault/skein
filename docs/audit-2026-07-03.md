Scope: full-codebase audit of `timeloop-vault/skein` at v0.2.5 (post-chapter-8), across
architecture, correctness, error handling, testing, security, performance, DX consistency and
docs. Every finding below marked **confirmed** survived an adversarial verification pass against
the actual code; **adjusted** means the core stands but the original claim needed correction
(corrections are folded in). Duplicate findings surfaced by multiple audit lenses are merged.

## 1. Executive summary & health assessment

Skein is in fundamentally good shape for what it is: a daily-driven, auto-updating prototype
whose Rust core (`crates/skein-git`, the PTY layer, the two harness adapters) is carefully
commented, deliberately scoped, and largely free of TODO rot — deferred work is consistently
routed to GitHub issues, and the issue tracker is unusually honest. The audit found **no
currently exploitable security hole and no data corruption in the happy path**.

Four themes dominate everything else:

1. **One traced total-data-loss path.** A single unparseable room blob (or transient DB read
   error) at boot fails `load_all` wholesale, the frontend sets `loaded=true` with `rooms=[]`,
   and the autosave immediately commits `DELETE FROM sessions` — every room, archived history
   and session link gone, with only an invisible `console.error`. This is the highest-stakes
   finding in the audit and is untracked.

2. **The safety net has holes exactly where the risk is.** The 89 Rust unit tests covering the
   4,300-LOC harness-parsing subsystem are never executed by any gate (the workspace excludes
   `app/src-tauri`), and the frontend — where nearly every shipped regression has lived
   (#153, #154, #159, #146, #62/#64/#124…) — has zero test infrastructure. A parser or
   notification regression would ship to the auto-update channel today.

3. **App.tsx (2,806 LOC, 2× since #19 was filed) is now producing bugs, not just smell.** The
   reopen/resume logic exists in three hand-mirrored copies and the third copy (OS-notification
   click un-archive) is missing the #153 fix — a live, repo-verifiable regression of a closed
   bug. Port allocation is copied four times, overlays are wired twice, and eleven ref-mirrors
   hold the []-dep'd listeners together by convention.

4. **The harness adapter pairs are the #116 abstraction gap made concrete.** Claude/opencode
   duplicate structs, persist loops, and classification logic, emit divergent payload shapes
   under the same action vocabulary, and have already drifted into user-visible bugs (#93's
   561-rows/244-distinct duplication, ts=0 mis-sorting). Copilot — half of the founding spec —
   is still a stub, and adding it on today's structure means a third hand-mirrored copy of
   everything.

Cross-cutting: heavy sync Tauri commands (git_diff per 200 ms watcher tick, whole-JSONL attach
parses, fsync'd wipe-and-reinsert saves) run on the **main thread**, making agent edit storms
the app's worst jank source; and failures across the adapter/persistence layer are logged at
`trace` (below the default filter) or swallowed entirely, so degradation is indistinguishable
from idleness. CLAUDE.md — read by an AI harness every session in an agent-driven repo — is
~7 chapters out of date and contains affirmatively false claims ("Tauri side has no tests yet").

**Recommended order of attack:** (1) close the boot-wipe path and add WAL/backup — hours of
work, existential stakes; (2) turn on the gates (run the 89 tests, add vitest + first table
tests); (3) fix the notification-click un-archive bug by extracting the shared unarchive helper
— the first slice of the #19 split; (4) rewrite CLAUDE.md; (5) then the two structural arcs in
parallel as capacity allows: main-thread/perf hardening and the #116 adapter consolidation.
Feature-wise, the ship-loop (stage/commit/land from the room) and the review surface (#52) are
the highest-leverage arcs; both should ride on the hardened foundation rather than precede it.

## 2. Confirmed findings, grouped by theme

Severity shown is the post-verification severity. `tracked:` names the open issue where one
exists; `tracked: —` means untracked today.

### Theme A — Data durability & persistence integrity

**A1. Failed `db_load_rooms` at boot arms the autosave with `[]` and wipes every persisted room** — **HIGH**, bug, tracked: —
Files: `app/src/App.tsx:1265-1280`, `app/src-tauri/src/db.rs:284-322`
`load_all` (db.rs:295) `?`-propagates the first serde error from ANY row, so one bad/shape-drifted
blob fails the entire load; the hydrate `.catch` (App.tsx:1265-1269) logs and sets
`loaded=true` while `rooms` is still `[]`; the autosave effect (deps `[rooms, loaded]`, guard
only `!loaded`) fires on the flip and `save_all` executes `DELETE FROM sessions` + reinsert of
nothing. Room has 7 required serde fields with no `#[serde(default)]` (db.rs:155-178), so a
future Rust-side field change, a downgrade across a type change, blob corruption, or a transient
read error ships the wipe. (Verification note: a crash mid-save does NOT corrupt — save_all is
transactional; the serde-drift and load-error triggers are the real ones.)
*Fix:* on load failure do NOT arm autosave (distinct `loadFailed` state + error UI); make
`load_all` skip-and-log bad rows; `#[serde(default)]` policy for new fields; rolling
`skein.db.bak` before first write of a run. → proposed issue.

**A2. Claude live tail replays the whole JSONL through the un-deduplicated live path on truncation or vanish-and-reappear** — **HIGH**, bug, tracked: **#93**
Files: `app/src-tauri/src/harness_events_claude.rs:378-388, 411-417, 469-472, 490-509`
Only attach-time backfill filters by `timestamp_ms > max_ts`; the live tick path persists with
no filter. Two paths reset `last_pos=0` (file vanished→reappeared; size < last_pos on
truncation/rewrite) and re-ingest every row: duplicate `harness_actions` rows (plain INSERT, no
UNIQUE), re-broadcast, and re-fired phase events. This is the confirmed mechanism behind #93's
dogfooded 561-rows/244-distinct/one-row-stored-112× data.
*Fix:* route resets through the dedup, or land #93's content-hash + `INSERT OR IGNORE` so both
paths are idempotent by construction. → hygiene update on #93.

**A3. opencode live SSE actions persist with `timestamp_ms=0`, mis-sorting the feed; trailing ts=0 parts get re-inserted once by the next backfill, older ones are permanently stranded** — **MEDIUM**, bug, tracked: **#93** (+ prompt:null half in **#91**)
Files: `app/src-tauri/src/harness_actions_opencode.rs:231, 246, 264, 353-375`
`extract_step_finish`/`extract_patch_part`/`extract_compaction` hard-code ts=0 (no wire time);
rows sort to the wrong end of every `ORDER BY timestamp_ms DESC` query. Backfill stamps the same
parts with opencode's `time_created`, so the ts=0 twin of anything newer than the last
real-timestamped row is duplicated once per re-attach; mid-session ts=0 rows never get a
corrected copy. The frontend payload-identity dedup (feedItems.tsx:322) exists specifically to
paper over this. *Fix:* stamp live rows with received-at wall clock; content-level dedup per #93.

**A4. skein.db runs at sqlite defaults (no WAL, no busy_timeout) behind one global mutex; opencode SSE loop does blocking fsync'd inserts on the tokio runtime thread** — **MEDIUM**, perf, tracked: —
Files: `app/src-tauri/src/db.rs:185-191, 421`, `app/src-tauri/src/harness_events_opencode.rs:358-420`, `app/src/App.tsx:1274-1280`
Zero PRAGMAs anywhere: every insert is its own journaled double-fsync transaction. Claude
debouncer threads, opencode tokio tasks (no `spawn_blocking`), per-transition frontend events,
and the every-rooms-change `db_save_rooms` wipe-and-reinsert all serialize through one
`Mutex<Connection>`, so a room-switch's 500-row backfill query queues behind fsync bursts.
*Fix:* `journal_mode=WAL`, `synchronous=NORMAL`, `busy_timeout` at open (3 lines); move opencode
inserts off the runtime thread. → proposed issue (combined with A5).

**A5. Claude adapter attach reads + parses the entire session JSONL twice, then backfills one fsync'd transaction per row** — **MEDIUM**, perf, tracked: —
Files: `app/src-tauri/src/harness_events_claude.rs:270, 490-509, 516-552`, `app/src-tauri/src/db.rs:421-439`
`fs::read_to_string` + full parse in `determine_initial_state`, then a second full parse in
`backfill_actions`, on every LiveTerminal mount, even when zero rows will be inserted; when rows
ARE inserted (first attach, or the A2 replay paths — real per #93) it's one unbatched
INSERT+fsync per row while holding the DB mutex, on the main thread. #165 bounded only the
frontend query. *Fix:* wrap backfill in one transaction; fuse the two passes; skip when file
size == high-water offset. Note: #93's proposed full-re-scan fix makes this strictly worse
unless inserts are batched first.

**A6. "Delete forever" keeps the room's full prompts and tool outputs in skein.db; both telemetry tables grow without bound** — LOW, privacy/hygiene, tracked: —
Files: `app/src/App.tsx:1356-1363`, `app/src-tauri/src/db.rs:418-436`, `harness_actions_claude.rs:566-577`
Tool results (Bash stdout etc.) are stored verbatim; `deleteRoomForever` only filters React
state (its own comment defers the vacuum). Second-copy privacy-expectation problem on a
single-user disk, not an exposure escalation; user prompts are already ~200-char truncated by
Claude. *Fix:* `DELETE ... WHERE room_id = ?` on delete-forever + a retention/vacuum pass.

### Theme B — App.tsx monolith & room-lifecycle duplication

**B1. App.tsx (2,806 LOC) monolith — duplication is now producing real bugs** — **HIGH**, arch, tracked: **#19** (stale numbers)
Files: `app/src/App.tsx:1071, 1631-1664, 2565-2586, 2781-2799, 1389-1393, 2764-2768`
Filed at 1,403 LOC; now exactly doubled. Verified duplications: (a) reopen/resume logic
triplicated (boot hydrate 1230-1256, reopenRoom 1313-1354, notification-click 2180-2188 — the
third copy missing the rewrite is B2 below); (b) opencode port-allocation + capture kickoff
copied four times (1230-1243, 1325-1335, 2261-2272, 2320-2331); (c) pending-clear `setRooms`
walk byte-identical twice (1685-1703 vs 1996-2010); (d) `topPendingHarness` re-inlined verbatim
in the status bar (1389-1393 vs 2763-2768); (e) all five overlays + toast stack wired in both
return branches; (f) eleven hand-rolled ref-mirrors keep []-dep listeners current by convention.
Commit 850c25b (fix #153) is repo-recorded proof the duplication bites: it patched reopenRoom by
mirroring the boot path and still missed the third copy.
*Fix (the right split now):* `useRoomsStore` (rooms state, sqlite mirror, archive/reopen/delete,
resumeCmd + port/session allocation — kills a+b), a notification-engine module (~450 LOC,
self-contained), `NewRoomDialog` to its own file, a `useDragReorder` hook, one `AppOverlays`
fragment, `buildPaletteItems`. Leaves App.tsx at ~600-800 LOC of layout + wiring.
→ hygiene: update #19 with current numbers and seams.

**B2. OS-notification-click un-archive skips the resume rewrite — reproduces closed #153 through a third code path** — **MEDIUM**, bug, tracked: —
Files: `app/src/App.tsx:2180-2198` vs `1313-1354` (the #153 fix) and `1251-1256` (boot hydrate); `app/src/ReopenRoomModal.tsx:5-7` (stale comment that likely caused the miss)
`onNotificationClicked` strips `archived` and activates the room with no `resumeCmd` rewrite and
no fresh port allocation. Archived rooms are unmounted (only `activeRooms` render), so
un-archiving remounts LiveTerminal and re-spawns the stored cmd verbatim. A Claude harness
created this app run still carries fresh-form `claude --session-id <uuid>`; respawning it hits
"Session ID is already in use" — the exact #153 failure. (opencode correction from verification:
the port usually rebinds fine; the real damage is a silent brand-new conversation, since the
fresh-form cmd lacks `--session`/`--continue`.) Window is narrow (notifyOs opt-in, macOS click
delivery, same-run archive) but it is a regression of a fixed bug class and the handler shipped
*before* the #153 fix — the fix simply missed the third copy.
*Fix:* extract one `unarchiveRoom(id)` (resumeCmd rewrite + port allocation) called from both
reopenRoom and the notification handler (route via ref — the handler is []-dep'd); update the
stale ReopenRoomModal header comment. → proposed issue.

**B3. Toast auto-dismiss timer resets on every App re-render — toasts persist under exactly the activity that spawns them** — **MEDIUM**, bug, tracked: —
Files: `app/src/App.tsx:144-147, 2525-2526`
The dismiss effect deps on `onDismiss`, a fresh inline closure per App render; any `setRooms`/
`setToasts` (badge bumps from other rooms, api_error coalesce — which itself replaces the toast
object, 1930-1932) restarts the 6 s timer. With two busy rooms transitioning <6 s apart, visible
toasts never expire — contradicting the code's own comment expecting error toasts to "lapse
between rows". *Fix:* arm once on mount reading `onDismiss` from a ref, or expiry timestamps in
ToastEntry swept by one interval. → proposed issue.

**B4. NewRoomDialog folder-validation cancellation is dead code — stale git responses clobber the newer path's verdict** — **MEDIUM**, bug, tracked: —
Files: `app/src/App.tsx:500-535` (`507`, `530`)
`let cancelled = false` and the `() => { cancelled = true }` "cleanup" both live inside the
`setTimeout` callback, whose return value goes nowhere; the effect's real cleanup only clears
the timeout. Once the timer fires, all `if (cancelled)` guards are permanently false, so a slow
`git_is_repo`/`git_branches` response for a superseded path overwrites the newer verdict — the
dialog can show "✓ git repo" for a non-repo folder and populate branches from the wrong repo,
persisting until the next edit (nothing re-validates on submit). *Fix:* hoist `cancelled` to
effect scope, set it in the effect cleanup. → proposed issue.

**B5. `closeHarness` always resets focus to `remaining[0]` and never prunes per-harness maps** — LOW, bug, tracked: —
Files: `app/src/App.tsx:1451-1462`
Closing a *background* tab yanks focus (and, via the displayed-harness effect, silently clears
the yanked-to tab's pending badge). `opencodePorts`, `lastBadgeAtRef`, `lastApiErrorAtRef` are
only ever added to — bounded leak, hygiene not correctness. *Fix:* only reassign when the closed
harness was active (pick the neighbor); prune the maps in close/delete.

**B6. `closeRoom` computes next-active from state captured before awaiting the native confirm** — LOW, bug, tracked: —
Files: `app/src/App.tsx:1293-1311`
Only awaited mutator in the file that reads render-captured `activeRooms`/`activeRoomId` instead
of the refs. Verification narrowed the reachable failure: the confirm is window-modal, so the
only mutator that can fire during it is the macOS notification-click handler — click a banner
for the room being closed while the dialog is up, confirm, and `activeRoomId` is left pointing
at an archived room (blank workspace until a tab click). *Fix:* re-read
`roomsRef`/`activeRoomIdRef` after the await; pick the neighbor tab.

**B7. Command palette shows "room · undefined" for non-git rooms** — LOW, bug, tracked: —
Files: `app/src/App.tsx:2413-2419` (`Room.branch?` per types.ts:63)
Unconditional `` hint: `room · ${r.branch}` ``; tab meta (App.tsx:384) and ReopenRoomModal
(177-183) both handle the branchless case correctly — the palette is the one surface that
doesn't. *Fix:* mirror the existing fallback.

**B8. Escape closes stacked overlays together (Settings' window listener fires under the palette)** — LOW, bug, tracked: —
Files: `app/src/SettingsModal.tsx:84-93`, `app/src/CommandPalette.tsx:46-50`, `ReopenRoomModal.tsx:110-115`
Mod+K opens the palette over Settings (no gating; and per verification the palette actually
opens *behind* Settings at the same z-index, silently stealing focus); Escape on the palette
input has no `stopPropagation`, so the same keydown also closes Settings. *Fix:*
`stopPropagation()` in the input handlers or a shared topmost-overlay stack; optionally gate
Mod+K while a modal is open.

**B9. `captureOpencodeSessionId` polls 5 minutes with no cancellation — an archived room's poll can steal a later session id** — LOW, bug, tracked: partially superseded by **#116** (scenario 3)
Files: `app/src/App.tsx:954-990, 2306, 2372`
Archived rooms stay in `roomsRef`, so their still-running poll can capture a newer harness's
session and persist it onto the archived harness, corrupting its future resume (capture
*blocking* additionally requires the new harness's SSE path to have failed; closed/deleted
harnesses are no-ops — narrower than originally claimed). *Fix:* thread a
`stillWanted()`/AbortSignal check per iteration; #116's SessionTracker supersedes the heuristic
long-term.

**B10. Keyboard copy combo unreachable at the post-exit prompt (Windows/Linux Ctrl+Shift+C no-ops)** — LOW, bug (heavily narrowed by verification), tracked: —
Files: `app/src/LiveTerminal.tsx:270-313`
The `exited` gate sits before the copy-combo branch. Verification refuted the headline ("output
of a crashed harness can't be copied"): native copy paths (macOS Edit-menu Cmd+C, plain Ctrl+C
fallthrough, right-click Copy) all still work. Residue: the *documented* Ctrl+Shift+C combo
silently no-ops post-exit and #158's empty-selection diagnostics don't run there. *Fix:* hoist
the copy branch above the exited gate (trivially safe).

### Theme C — Harness adapter layer (the #116 gap)

**C1. Claude/opencode adapter pairs are near-total duplicates with per-harness payload shapes leaking through the shared action vocabulary** — **HIGH**, arch, tracked: **#116** (foundation), fragments in #69/#93
Files: `harness_actions_claude.rs:60, 332, 344, 359-417`, `harness_actions_opencode.rs:32, 179, 187, 197-235`, `harness_events_claude.rs:516-563`, `harness_events_opencode.rs:153-159, 392-421`, `lib.rs:257-263`
Verified duplication: `ExtractedAction` defined byte-identically twice; `classify_tool`,
`files_touched`, `extract_patch_info`, `extract_plan_item` each duplicated with *divergent*
payload shapes under the same `action_kind` (patch: `structured_patch/user_modified` vs
`diff/file`; plan_change: create/update deltas vs full-snapshot writes; turn_cost: zero shared
fields); persist+broadcast loop and max-ts lookup written twice; two structurally identical
managers with four per-harness attach/detach commands; two 7-variant phase enums hand-mirrored
in TS (#69). The frontend quarantines the divergence in one normalization layer
(toolRows.tsx:3: "This is where every Claude↔opencode payload divergence lives") but the two
sides have already drifted into bugs (#93 ts=0, isSidechain asymmetry), and every data-layer fix
lands twice. *Fix sketch (feeds #116):* one shared `PhaseEvent` enum + Channel type (also
collapses #69), a `HarnessAdapter` trait with an `ActionSink` owning persistence + dedup policy
in ONE place, one manager + one attach command with a session-locator enum
(`JsonlSession{cwd,session_id}` | `SseServer{port,session_id}`), and normalized per-kind payload
contracts enforced by shared builders. The locator enum is the natural home for #116/#98's
"session changed under us" tracking. → hygiene: this is the design meat of #116.

**C2. Synthetic `SessionIdle` fires on every SSE reconnect, flipping a mid-turn opencode harness to "waiting" and firing a false "your turn" notification** — **MEDIUM**, bug, tracked: —
Files: `harness_events_opencode.rs:316-330, 63-66`, `app/src/harnessEvents.ts:227-230`, `app/src/App.tsx:1775-1783`
`stream_events` emits `Connected` + synthetic `SessionIdle` on EVERY handshake; the enum doc
("exactly once per attach") is false. opencode broadcasts `session.status` only on transitions,
so after a mid-turn drop no corrective `busy` arrives; the frontend maps `session_idle` →
`setWaitingFromAdapter`, and running→waiting is unconditionally notify-worthy (badge + toast +
OS banner, no `hasUserInput` gate). Self-corrects on the next delta, but the fired notification
is unrecallable. **Fix caveat from verification:** do NOT gate `Connected` itself — the frontend
deliberately relies on it re-firing to re-arm the authoritative source after `SessionEnd`; and
naively gating the synthetic idle on first-connect introduces the opposite bug (turn ended
during the outage → stuck "running" forever). Right fix: a distinct baseline-idle signal the
frontend applies without treating it as a notify-worthy transition (relates to #143's
idle/waiting rethink). → proposed issue.

**C3. `stream_events` can panic via `unwrap_err` on a non-2xx, non-error HTTP status, silently killing the adapter task** — LOW, bug, tracked: —
Files: `harness_events_opencode.rs:308-312`
`is_success()` is false for 1xx/3xx but `error_for_status()` only errs on 4xx/5xx → 1xx/304/
Location-less 3xx panics `unwrap_err` inside a task whose JoinHandle (`_handle`) is never
awaited: adapter dies silently, harness falls back to heuristics. Reachable via the acknowledged
`pick_free_port` TOCTOU or the indefinite reconnect loop hitting a reclaimed port. *Fix:*
construct an explicit retryable error from the status.

**C4. SSE frame parser only recognizes `\n\n`, not spec-legal CRLF framing** — LOW, latent hardening, tracked: —
Files: `harness_events_opencode.rs:426-428, 375, 347`
Pure-CRLF framing would never complete a frame: silent stall + unbounded carry buffer, no error
surface. No current trigger (direct localhost reqwest connection, opencode emits `\n\n`; the
"trailing \r breaks serde" sub-claim was refuted — CR is JSON whitespace). *Fix:* accept both
separators, trim trailing `\r`, cap the carry buffer with a warn.

**C5. Singular `toolUseResult` attaches to the first tool_result block with no id matching; `pending` never ages out within an attach** — LOW, hardening, tracked: —
Files: `harness_actions_claude.rs:72-84, 229-257` (test at 883 bakes the assumption in)
Verification: multi-result user rows have never been observed in real transcripts (recon doc,
681 rows), interrupts write synthetic results that close pending entries, and the extractor is
recreated per attach — so both halves are defensive-code territory. Worst case: missing/shifted
rich payload on one Live Context card. *Fix:* attach structured result only when the row has
exactly one tool_result; evict pendings at turn boundaries and emit `interrupted: true` rows.

**C6. `opencode_db_path` hardcodes `~/.local/share/opencode` — XDG_DATA_HOME relocation silently degrades fallback capture, backfill, and boot staleness validation** — LOW, bug, tracked: — (#116 hardcodes the same path in its own body)
Files: `app/src-tauri/src/resume.rs:14-21, 42-44`, `harness_actions_opencode.rs:320-324`
With XDG_DATA_HOME set (Linux; terminal-launched dev on macOS) the opencode child honors it but
Skein reads `~/.local/share`: backfill silently returns 0 and — worse than a no-op — boot
staleness validation actively drops *valid* captured session ids. SSE remains the primary
capture path, so impact is narrow on the owner's platforms. *Fix:* honor XDG_DATA_HOME; log when
the db exists but a directory query returns nothing (the `directory = ?1` exact-match is
fragile in principle but no concrete repro).

**C7. `claude_session_exists` collapses I/O errors to `false`, making the frontend's documented keep-on-error policy unenforceable for Claude** — LOW, bug, tracked: —
Files: `app/src-tauri/src/resume.rs:84-100`, `app/src/App.tsx:1183-1201, 1211-1217`
A transient `read_dir` failure of `~/.claude/projects` at boot is indistinguishable from
"session gone" → sessionId stripped and the strip persisted. Recoverable via `claude --resume`'s
interactive picker; opencode's twin already returns `Result` and is handled correctly (the
original "Windows drops ALL opencode ids" claim was refuted — capture and check share the same
path helper, and 496c140 fixed home resolution). *Fix:* return `Result<bool>` distinguishing
"provably absent" from "could not check".

**C8. `add_worktree` creates the branch before the name/duplicate checks — late failures strand an orphan branch** — LOW, bug, tracked: —
Files: `crates/skein-git/src/lib.rs:234-267`
Verification correction: in the real UI flow branch and worktree name derive from the same slug
and nothing ever deletes either, so a reused slug fails FIRST at `branch()` with no state
mutated (the tidy `WorktreeExists` error is effectively dead code for the UI); the orphan needs
out-of-band surgery (which #164 shows users do) or fs errors. *Fix:* reorder checks before
branch creation or delete the branch on failure; add duplicate-path tests (none exist).

### Theme D — Silent failure & observability

**D1. harness_actions insert failures and opencode backfill errors are invisible (trace-level logs below the default `info` filter; `backfill_from_db` returns bare 0)** — **MEDIUM**, error-handling, tracked: #93 covers dedup, NOT the invisibility
Files: `harness_events_claude.rs:546-549`, `harness_events_opencode.rs:416-419`, `harness_actions_opencode.rs:320-346, 371, 418`, `lib.rs:110-111`
A disk-full/sqlite error or an opencode schema change makes Live Context rows vanish with
literally no log line at any level; "parser broken" is indistinguishable from "nothing
happened". (Verification: the emit-failure trace in harness_action_event.rs is deliberate
best-effort and fine.) *Fix:* warn-level persistence failures, per-adapter dropped-row counter,
reasoned early-return logging in backfill. → proposed issue (combined with D2).

**D2. Live Context / L2c degradation is invisible: attach failures, missing ports, and backfill errors all render as "no activity"** — **MEDIUM**, error-handling, tracked: —
Files: `app/src/harnessEvents.ts:71-75, 175-179`, `app/src/App.tsx:2269, 1235`, `app/src/liveContext/store.ts:152-158`
Verified end-to-end: attach rejection → console.warn + silent degradation to the 8 s heuristic
AND permanently empty Activity/Plan/Diff cards (DiffCard derives tabs solely from harness
actions, so even live git data becomes unreachable); all four `pick_free_port` failure sites
proceed portless with warn only; backfill failure renders idle-room chrome. Four independent
silent paths breaking the product's core observability promise. *Fix:* per-harness
attach/degraded flag in the existing harnessActivity store + a muted "live feed unavailable"
banner; error row instead of empty-state on backfill failure. Pairs with a cheap
format-drift detector (unknown stop_reason/status → amber "adapter degraded" state), since all
parsing is fail-silent by design and #144/#145 proved the formats move.

**D3. Diff card swallows `git_diff` and `git_watch_start` failures** — LOW, error-handling, tracked: — (#114 is the related-but-different staleness issue)
Files: `app/src/liveContext/useWorktreeDiff.ts:28-32, 50-52`

### Theme E — Performance & main-thread hazards

**E1. Heavy synchronous Tauri commands execute on the main thread** — **HIGH**, perf, tracked: —
Files: `app/src-tauri/src/lib.rs:292, 378, 624`, `git.rs:241`, `harness_events_claude.rs:270`, `pty.rs:328`
Exactly one command is `async` (`opencode_events_attach`); everything else — `git_diff` (full
hunk text incl. untracked content, invoked per 200 ms watcher tick), `claude_events_attach`
(whole-JSONL read + double parse + per-row inserts, per mount, serialized at boot),
`db_save_rooms` (fsync'd wipe-and-reinsert per rooms change), `pty_spawn` — runs on the
main/event-loop thread. During an agent edit storm, pty_write keystrokes and all pending IPC
queue behind back-to-back diffs; the app visibly stutters exactly when agents work. *Fix:* mark
the heavy commands async; move claude attach I/O to a spawned thread. → proposed issue.

**E2. Watcher-driven `git_diff` refetch is unbounded and uncoalesced** — **HIGH**, perf, tracked: —
Files: `app/src/liveContext/useWorktreeDiff.ts:24-40`, `app/src-tauri/src/watcher.rs:18`, `crates/skein-git/src/lib.rs:397-482`, `app/src/liveContext/DiffCard.tsx:31-51`
No in-flight guard (invokes pile up when the diff outlasts the 200 ms debounce), no payload cap
(one large untracked generated file = per-line DiffLine structs serialized over IPC per tick),
watcher fires ~5 ticks/s for the whole duration of builds inside the worktree, no deep-equal
check before `setFiles`, unvirtualized unmemoized line rendering — and the watcher/refetch runs
even with the Diff card collapsed (the `visible` gate isn't composed with `layout.collapsed`
like Activity's). Combined with E1 this is the app's worst-case jank source. *Fix:* in-flight
coalescing, per-file/total diff budgets with an oversize marker, skip identical payloads, gate
on card collapse. → proposed issue.

**E3. Live Context re-derives everything O(n) with repeated `JSON.parse` per live event, over an unboundedly growing actions array — including for hidden rooms** — **MEDIUM**, perf, tracked: — (#165 bounded only boot backfill)
Files: `app/src/liveContext/store.ts:59-61`, `ActivityCard.tsx:135`, `DiffCard.tsx:82, 114`, `plan.ts:156`, `feedItems.tsx:261`, `LiveContext.tsx:87-135`, `useGitBranchWatcher.ts:15-58`
Per event: `mergeById` rebuilds a full id Set despite `idsRef` existing to avoid exactly that;
`orderForDisplay` (O(n log n)) computed twice (and lives in the ActivityCard *component* file,
imported by DiffCard); flattenFeed/deriveTabs/autoFocusFile/`harnessPatchHunks` (unmemoized, in
the render body, on the always-taken #114 fallback path) each independently re-parse all patch
payloads (KBs-tens of KBs each); no parse cache anywhere. All of this also runs for every
*hidden* mounted room on its own live events, and `useGitBranchWatcher` runs an always-on
recursive FS watcher per mounted room (no `visible` gate — in pointed contrast to
useWorktreeDiff, whose comment explains why the gate exists), with the visible room running a
second watcher on the same cwd. *Fix:* WeakMap parse cache (or parse-at-ingest), hoist
orderForDisplay to one shared memo in a data module, memoize harnessPatchHunks, use idsRef in
mergeById, gate/share the branch watcher. → proposed issue.

**E4. `probe_login_shell_path` runs `$SHELL -ilc` with no timeout — a blocking rc file freezes the entire app** — **MEDIUM**, bug, tracked: — (#72/#3/#1 cover PATH content/choice, not the hang)
Files: `app/src-tauri/src/pty.rs:322-351, 139`
`Command::output()` with no deadline, cached in a OnceLock evaluated inside the first
`pty_spawn` — which is a sync command, so a hang freezes the whole IPC/event loop (worse than
originally claimed), silently, unrecoverably. Verification corrections: stdin is already nulled
by `output()` (interactive-prompt scenario refuted); real hang modes are rc files blocking on
network/locks or spawning background processes that inherit the pipes. *Fix:* deadline-polled
child, kill on expiry, fall back to inherited PATH + augment_path. → proposed issue (with E5).

**E5. `pty_write` holds the manager-wide mutex across a blocking write — a wedged child deadlocks every PTY op including `pty_kill`** — **MEDIUM**, bug, tracked: —
Files: `app/src-tauri/src/pty.rs:254-262, 264-286`
`write_all`+`flush` on the PTY master under the single map mutex; a stopped/non-reading child
plus a multi-KB paste (real tty input buffers are ~4 KB, not 64 KB — MORE reachable than
claimed) blocks the write forever, and spawn/resize/kill for every harness block behind it — the
recovery action is itself deadlocked. *Fix:* don't hold the map lock across I/O (per-PTY writer

## Appendix: refuted claims (checked and dismissed — do not re-report)

1. **"list_dir uses metadata() not symlink_metadata() — symlinks never reported, broken
   symlinks disappear"** (reported twice, refuted twice). Confusion between `std::fs::metadata`
   and `DirEntry::metadata` — the latter does NOT traverse symlinks (lstat semantics). Verified
   empirically: dangling symlinks list fine with kind "symlink". Behavior matches the comment's
   intent; at most a comment-phrasing nit.
2. **"Concurrent fire-and-forget db_save_rooms can commit out of order (stale-state
   rollback)"**. Premise wrong: sync Tauri commands run inline in the IPC protocol handler on a
   single thread, one at a time in arrival order; two rapid saves from the single JS thread
   cannot reorder. (The *debounce/backup* concerns remain as unverified debt; the ordering
   hazard does not exist.)
3. **"Adapter detach can race a still-pending attach, leaking a Rust-side adapter for a dead
   harness"**. For the cited Claude path, impossible: both commands are sync and serialize in
   IPC order — detach cannot overtake an attach mid-file-read. The only theoretical gap is the
   async opencode attach vs sync detach, with a microseconds window, self-healing consequences,
   and not the scenario claimed.
4. **Partial refutations folded into findings above** (for the record): the "opencode SSE
   adapter attaches to nothing after un-archive" sub-claim of B2 (port usually rebinds; real
   harm is a fresh conversation); the "trailing \r breaks serde_json" sub-claim of C4; the
   "keystrokes to a dead writer vanish with no surface" scenario of D4 (exit banner + key
   swallowing already handle it); the "crashed-harness output can't be copied" headline of B10
   (native copy paths work); the "Windows drops ALL opencode resume ids at boot" scenario of C7
   (capture and check share the same path helper); the "closeRoom picks a room
   archived/deleted during the dialog" mechanism of B6 (dialog is window-modal; only the
   notification handler can mutate); the "rollback-after-auto-update breaks deserialization"
   trigger of A1 (unknown *added* fields are ignored; only removed/renamed/retyped fields or
   corruption trigger it).
