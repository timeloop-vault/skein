The daemon-owned terminal

One program reads what a harness prints. Every screen only draws what it is sent.

Today the app's terminal reads the harness's output and draws the screen. The first design for the detached daemon added a second reader in the daemon, to rebuild the screen after a reconnect. Two readers of the same output can disagree, and the gap cannot be fixed without patching a reader. The new design keeps one reader, in the daemon. The app, and any later client, only draws what the daemon sends. This is the tmux and mosh model.

Before: the first design had two readers

Source. Renders: docs/skeind-terminal-design.md, section "The flow" (old). Non-normative: the text is authoritative.

  1. The harness writes bytes to its PTY.
  2. The daemon's reader and coalescer batch them (16 ms, 64 KB).
  3. The daemon forwards the raw bytes to the app.
  4. xterm.js in the app reads them and draws.
  5. A second reader in the daemon reads the same bytes, for the snapshot after a reconnect. This second reader exists in the first P2b design only.

After: one reader, dumb viewers

Source. Renders: docs/skeind-terminal-design.md, sections "The flow" (new) and "The frame". Non-normative: the text is authoritative.

  1. The harness writes bytes to its PTY.
  2. The daemon feeds them to that PTY's engine, the only reader. The engine answers the harness's device queries itself.
  3. The engine keeps the grid. History rows that leave the screen stay in the engine, and it counts them.
  4. The frame scheduler waits for the coalescing window and for any synchronized update to finish.
  5. For each viewer, the encoder compares the grid with what that viewer was last sent. It writes one frame in a small fixed set of VT sequences.
  6. The client writes the frame into its terminal widget, which draws it. A phone widget could do the same later.
  7. Daemon features (Hermes screen phase, prompt delivery, pane notices) read the engine, with or without a client.

How it reaches main without breaking Skein

Source. Renders: docs/skeind-terminal-design.md, sections "Delivery" and decision T4. Non-normative: the text is authoritative.

  1. The engine, the encoder and the test gate land as library code. Nothing calls them in the product.
  2. The fan-out and the frame path land behind the flag. With the flag unset, every byte takes today's path.
  3. The daemon learns to read its own screen and to author pane notices, then the view learns the frame mode. Both only when the flag is on.
  4. Dogfood with the flag on, on the dev and local-release profiles.
  5. The flip: frames become the only path. The raw path, the flag and the helpers are deleted.
  6. The socket work and the cutover follow the flip.

What the app still does itself

  • Input encoding: keys, mouse and paste. It uses the modes the daemon mirrors, and sends the bytes.
  • Selection and copy: local, over the app's own screen and scrollback.
  • Scrollback browsing: local. The daemon fills it, up to 5000 rows.
  • Links: the daemon re-sends them, and the app's link handler is unchanged.
